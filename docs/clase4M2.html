01PUNTO DE PARTIDA

Una API funcional todavía puede ser una API ingenua

Problema de negocio

Si una tienda acepta un producto con precio de −$5.000, ¿falló la persona que escribió el dato o el sistema que decidió guardarlo?

El backend es la última frontera antes de la base de datos. No puede confiar en que un formulario, otra aplicación o una persona siempre enviarán información correcta. Debe verificar cada entrada y responder de manera predecible cuando algo no cumple las reglas.

Catálogo de tienda

El salto profesional

Producto y Categoría ya crean y consultan registros. El siguiente paso es completar el ciclo CRUD, impedir datos inválidos, traducir errores técnicos y publicar un manual navegable de la API.

El recorrido de una petición

Cliente → Controller y DTO → Service → Prisma → Base de datos. El controller protege la entrada; el service coordina el caso de uso; Prisma ejecuta la persistencia. Cada capa tiene una responsabilidad distinta.

Punto actual

POST y GET funcionan en Producto y Categoría. El ValidationPipe ya está activo.

Problema visible

El precio negativo sigue entrando porque el DTO existe, pero el controller no lo está usando como clase.

Resultado esperado

Producto, Categoría y Usuario con CRUD; errores 400, 404 y 409; documentación disponible en /docs.

Antes de modificar

Confirma que npm run start:dev, GET /productos y GET /categorias funcionan. Si falta el cliente generado de Prisma, ejecuta npx prisma generate.

02VALIDACIÓN EN EJECUCIÓN

El DTO debe existir cuando la aplicación está corriendo

Definición técnica

Los type e interface de TypeScript se eliminan al compilar. Una clase permanece en JavaScript y puede conservar metadatos de decoradores para class-validator.

En palabras sencillas

Un type ayuda al editor, pero no puede detener una petición. Una clase DTO sí puede convertirse en la puerta de control del backend.

Analogía

Decir “el paquete debe pesar menos de 5 kg” no controla nada. Poner una balanza en la entrada permite verificarlo y rechazarlo.

Predice el comportamiento

Si el DTO tiene @Min(0), pero @Body() usa un type, ¿por qué no aparece el error?
Porque el type ya no existe en tiempo de ejecución. El pipe no recibe una clase con metadatos de validación y no encuentra reglas que aplicar.

Qué vamos a hacer

Conectaremos CrearProductoDto directamente con el cuerpo del endpoint.

Por qué lo hacemos

El ValidationPipe necesita una clase real para descubrir y ejecutar sus decoradores.

Qué aprenderás

A distinguir el tipado de desarrollo de la validación que ocurre en ejecución.

REEMPLAZARsrc/productos/productos.controller.ts
import {
  Body,
  Controller,
  Get,
  Param,
  ParseIntPipe,
  Post,
} from '@nestjs/common';
import { ProductosService } from './productos.service';
import { CrearProductoDto } from './dto/crear-producto.dto';

@Controller('productos')
export class ProductosController {
  constructor(private readonly productosService: ProductosService) {}

  @Post()
  crear(@Body() body: CrearProductoDto) {
    return this.productosService.crear(body);
  }

  @Get()
  obtenerTodos() {
    return this.productosService.obtenerTodos();
  }

  @Get(':id')
  obtenerPorId(@Param('id', ParseIntPipe) id: number) {
    return this.productosService.obtenerPorId(id);
  }
}

La línea decisiva es @Body() body: CrearProductoDto. El controller recibe la clase; los decoradores se ejecutan; solo después el service recibe datos validados.

Configuración global ya activa

whitelist limita el cuerpo a propiedades declaradas; forbidNonWhitelisted rechaza campos adicionales; transform transforma valores cuando existe información suficiente sobre el tipo esperado.

  1. 01

    Envía un producto válido: debe responder 201.

  2. 02

    Envía {"precio": -5000}: debe responder 400 y señalar la regla @Min(0).

  3. 03

    Agrega "hackeo": true: debe responder 400 porque esa propiedad no pertenece al contrato.

Responsabilidad de capa

El service puede usar un type para autocompletado porque no es la puerta de entrada. La validación externa pertenece al DTO que usa el controller.

03CRUD DE PRODUCTO

Actualizar lo necesario y eliminar por identidad

Create

POST crea un recurso.

Read

GET consulta uno o varios recursos.

Update

PATCH modifica solo los campos enviados.

Delete

DELETE elimina el recurso identificado en la URL.

PUT frente a PATCH

PUT reemplaza la representación completa. PATCH aplica un cambio parcial. Si solo cambia el precio, PATCH evita reenviar nombre, descripción, stock y categoría.

Qué vamos a hacer

Crearemos un DTO de actualización basado en el DTO de creación.

Por qué lo hacemos

Las reglas deben mantenerse en un solo lugar; solo cambia que los campos serán opcionales.

Qué aprenderás

A reutilizar contratos con PartialType sin duplicar validaciones.

EJECUTARTerminal · raíz de catalogo-api
npm install @nestjs/mapped-types
CREARsrc/productos/dto/actualizar-producto.dto.ts
import { PartialType } from '@nestjs/mapped-types';
import { CrearProductoDto } from './crear-producto.dto';

export class ActualizarProductoDto extends PartialType(CrearProductoDto) {}

PartialType conserva los decoradores originales. Un precio enviado sigue obligado a ser mayor o igual a cero, pero es válido omitirlo si se actualiza otro campo.

Qué vamos a hacer

Añadiremos las operaciones de actualización y eliminación en la capa que conversa con Prisma.

Por qué lo hacemos

El controller expone HTTP; el service concentra las operaciones del dominio y la persistencia.

Qué aprenderás

A traducir PATCH y DELETE en operaciones update y delete de Prisma.

AGREGAR ARRIBAsrc/productos/productos.service.ts
type ActualizarProductoInput = {
  nombre?: string;
  descripcion?: string;
  precio?: number;
  stock?: number;
  categoriaId?: number;
};

actualizar(id: number, datos: ActualizarProductoInput) {
  return this.prisma.producto.update({
    where: { id },
    data: datos,
    include: { categoria: true },

eliminar(id: number) {
  return this.prisma.producto.delete({
    where: { id },
  });
}

Qué vamos a hacer

Expondremos las dos operaciones mediante rutas con un identificador numérico.

Por qué lo hacemos

La URL identifica el recurso; el cuerpo describe el cambio parcial.

Qué aprenderás

A combinar decoradores HTTP, parámetros, pipes y DTO.

REEMPLAZARsrc/productos/productos.controller.ts
import {
  Body,
  Controller,
  Delete,
  Get,
  Param,
  ParseIntPipe,
  Patch,
  Post,
} from '@nestjs/common';
import { ProductosService } from './productos.service';
import { CrearProductoDto } from './dto/crear-producto.dto';
import { ActualizarProductoDto } from './dto/actualizar-producto.dto';

@Controller('productos')
export class ProductosController {
  constructor(private readonly productosService: ProductosService) {}

  @Post()
  crear(@Body() body: CrearProductoDto) {
    return this.productosService.crear(body);
  }

  @Get()
  obtenerTodos() {
    return this.productosService.obtenerTodos();
  }

  @Get(':id')
  obtenerPorId(@Param('id', ParseIntPipe) id: number) {
    return this.productosService.obtenerPorId(id);
  }

  @Patch(':id')
  actualizar(
    @Param('id', ParseIntPipe) id: number,
    @Body() body: ActualizarProductoDto,
  ) {
    return this.productosService.actualizar(id, body);
  }

  @Delete(':id')
  eliminar(@Param('id', ParseIntPipe) id: number) {
    return this.productosService.eliminar(id);
  }
}

Error frecuente

Qué aparece: Cannot find module '@nestjs/mapped-types'.

Cómo leerlo: el nombre entre comillas es el paquete que TypeScript no puede resolver.

Cómo resolverlo: ejecuta npm install @nestjs/mapped-types desde la raíz del proyecto.

04IA CON CRITERIO

Replicar un patrón después de comprenderlo

Decisión profesional

Producto ya tiene el patrón correcto. ¿Qué parte debe acelerar la IA y qué parte sigue siendo responsabilidad del desarrollador?

Copiloto, no piloto

La IA puede trasladar una estructura conocida a otra entidad. Tú defines el patrón, aportas las restricciones del dominio y verificas que el resultado conserve DTO, rutas, inyección de dependencias y operaciones Prisma correctas.

Categoría

Mismo ciclo, contrato más pequeño

Categoría necesita crear, consultar, actualizar y eliminar, pero solo expone nombre. El patrón de Producto se reutiliza; las reglas del dominio cambian.

Qué vamos a hacer

Crearemos los contratos que la IA debe respetar antes de pedirle el CRUD restante.

Por qué lo hacemos

Un prompt es más verificable cuando parte de archivos y restricciones explícitas.

Qué aprenderás

A separar las decisiones humanas del trabajo mecánico que puede acelerar una herramienta.

Replica ese patrón para `categorias`.

Revisión obligatoria

No aceptes la respuesta por apariencia

  1. 01

    Comprueba que @Body() use las clases CrearCategoriaDto y ActualizarCategoriaDto, nunca un type.

  2. 02

    Verifica @IsString(), @IsNotEmpty(), PartialType y ParseIntPipe.

  3. 03

    Confirma que el service use this.prisma.categoria y que cada ruta llame al método correspondiente.

  4. 04

    Prueba datos válidos, nombre vacío, identificador inexistente y el ciclo CRUD completo.

Límite de la IA

La herramienta puede replicar una forma incorrecta, olvidar un import o usar un modelo Prisma distinto. La compilación y las pruebas son evidencia; una respuesta convincente no lo es.

Dos controles diferentes

¿Qué diferencia existe entre @IsEmail() y @unique?
@IsEmail() valida la forma del dato recibido. @unique protege la regla de que no existan dos registros con el mismo correo. Un email puede tener formato válido y aun así estar repetido.
06MANEJO PROFESIONAL DE ERRORES

Traducir errores de Prisma al lenguaje de HTTP

2xx

La operación se completó: 200 OK, 201 Created.

4xx

La petición no puede atenderse así: 400, 404, 409.

5xx

El servidor falló de forma inesperada: 500 Internal Server Error.

Traducción necesaria

Prisma conoce la causa; HTTP comunica el resultado

P2025 indica un registro inexistente, P2002 una restricción única violada y P2003 una referencia inválida. Un filtro global convierte esos detalles de persistencia en respuestas útiles para cualquier cliente.

Qué vamos a hacer

Crearemos un Exception Filter que intercepte errores conocidos de Prisma.

Por qué lo hacemos

La API debe responder con semántica HTTP coherente sin repetir try/catch en cada service.

Qué aprenderás

A resolver una preocupación transversal en un único punto global.

CREARsrc/prisma/prisma-exception.filter.ts
import {
  ArgumentsHost,
  Catch,
  ExceptionFilter,
  HttpStatus,
} from '@nestjs/common';
import { Response } from 'express';
import { Prisma } from '../generated/prisma/client';

@Catch(Prisma.PrismaClientKnownRequestError)
export class PrismaExceptionFilter implements ExceptionFilter {
  catch(exception: Prisma.PrismaClientKnownRequestError, host: ArgumentsHost) {
    const response = host.switchToHttp().getResponse<Response>();

    let status = HttpStatus.INTERNAL_SERVER_ERROR;
    let mensaje = 'Error interno del servidor';

    if (exception.code === 'P2025') {
      status = HttpStatus.NOT_FOUND;
      mensaje = 'El registro solicitado no existe';
    }

    if (exception.code === 'P2002') {
      status = HttpStatus.CONFLICT;
      mensaje = 'Ya existe un registro con ese valor único';
    }

    if (exception.code === 'P2003') {
      status = HttpStatus.BAD_REQUEST;
      mensaje = 'La referencia indicada no existe';
    }

    response.status(status).json({ statusCode: status, message: mensaje });
  }
}

El import de Prisma usa ../generated/prisma/client porque este proyecto configuró una salida personalizada para el cliente. Copiar un import genérico desde internet rompería la compilación.

Qué vamos a hacer

Registraremos el filtro una vez para toda la aplicación.

Por qué lo hacemos

Producto, Categoría, Usuario y futuros módulos deben compartir el mismo contrato de errores.

Qué aprenderás

A activar infraestructura transversal durante el arranque de NestJS.

AGREGAR IMPORTsrc/main.ts
import { PrismaExceptionFilter } from './prisma/prisma-exception.filter';
AGREGAR EN BOOTSTRAPsrc/main.ts · después de useGlobalPipes
app.useGlobalFilters(new PrismaExceptionFilter());
  1. P2025

    Registro inexistente → 404 Not Found.

  2. P2002

    Valor único repetido → 409 Conflict.

  3. P2003

    Referencia inexistente → 400 Bad Request.

07DOCUMENTACIÓN VIVA

Una API profesional se explica sola

OpenAPI

Especificación estándar para describir endpoints, parámetros, cuerpos y respuestas de una API HTTP.

Swagger UI

Interfaz web que representa esa especificación y permite ejecutar peticiones desde el navegador.

Valor real

Frontend, QA y otros equipos pueden descubrir y probar la API sin adivinar rutas ni cuerpos.

Qué vamos a hacer

Instalaremos el módulo oficial de NestJS para generar documentación OpenAPI.

Por qué lo hacemos

La documentación debe evolucionar con las rutas y poder probarse desde una interfaz común.

Qué aprenderás

A publicar un contrato navegable en /docs.

EJECUTARTerminal · raíz de catalogo-api
npm install @nestjs/swagger
AGREGAR IMPORTsrc/main.ts
import { DocumentBuilder, SwaggerModule } from '@nestjs/swagger';
AGREGAR ANTES DE APP.LISTENsrc/main.ts · función bootstrap
const config = new DocumentBuilder()
  .setTitle('Catálogo API')
  .setDescription('API de la tienda: productos, categorías y usuarios')
  .setVersion('1.0')
  .build();

const documento = SwaggerModule.createDocument(app, config);
SwaggerModule.setup('docs', app, documento);

Prueba en navegador

http://localhost:3000/docs

Expande una ruta, selecciona “Try it out”, completa los datos y ejecuta la petición. La interfaz muestra URL, cuerpo, código de estado y respuesta.

Si /docs responde 404

Cómo leerlo: NestJS no registró esa ruta durante el arranque.

Qué revisar: que @nestjs/swagger esté instalado y SwaggerModule.setup se ejecute antes de app.listen.

Mejora posterior

Usa @ApiProperty() en los DTO para enriquecer ejemplos y esquemas. La documentación aporta valor cuando refleja el contrato real, no cuando solo enumera rutas.

08EVIDENCIA DE FUNCIONAMIENTO

Probar el sistema completo, no archivos aislados

Estrategia

Una compilación correcta demuestra que el código tiene forma válida. Las peticiones demuestran comportamiento. Recorre caminos felices, datos inválidos y conflictos de base de datos.

Producto

Ciclo CRUD y validación heredada

  1. 01

    POST /productos crea un producto válido y responde 201.

  2. 02

    GET /productos confirma que fue persistido.

  3. 03

    PATCH /productos/1 con {"precio": 999} conserva los demás campos.

  4. 04

    El mismo PATCH con {"precio": -50} responde 400.

  5. 05

    DELETE /productos/1 elimina el registro.

Errores traducidos

La respuesta debe explicar el caso

  1. 404

    PATCH /productos/999 y DELETE /productos/999 indican que el registro no existe.

  2. 409

    Crear dos usuarios con el mismo email produce conflicto en el segundo intento.

  3. 400

    Crear un producto con una categoriaId inexistente comunica referencia inválida.

Documentación

Un tercero debe poder descubrir la API

  1. 01

    Abre http://localhost:3000/docs.

  2. 02

    Confirma que aparecen productos, categorías y usuarios con sus verbos.

  3. 03

    Ejecuta al menos un POST y un PATCH desde Swagger UI.

Criterio técnico

¿La API está lista si Swagger carga, pero todavía acepta un precio negativo?
No. Swagger mejora descubrimiento y pruebas, pero no sustituye las reglas del dominio. La calidad depende de que contrato, validación, persistencia, errores y documentación sean coherentes entre sí.
09SIGUIENTE NIVEL

De CRUD a lógica de negocio

Nueva frontera

Crear un pedido implica guardar datos, calcular el total y descontar stock. ¿Qué ocurre si una de esas operaciones falla a mitad del proceso?

Transacción

Grupo de operaciones de base de datos que se confirma completo o se revierte completo.

En Prisma

prisma.$transaction permite coordinar el bloque todo-o-nada.

Analogía

En una transferencia, restar de una cuenta y sumar en otra deben suceder juntas. Un resultado a medias corrompe el negocio.

Reto guiado

Pedido con stock consistente

Construye un módulo pedidos que haga visible una regla que no puede resolverse con CRUD genérico.

  1. 01

    Crea POST /pedidos para recibir usuario, productos y cantidades. El cliente no envía un total confiable.

  2. 02

    Dentro de una transacción, consulta precios, calcula el total, crea pedido y detalles, y descuenta stock.

  3. 03

    Si no existe stock suficiente, responde 400 y comprueba que no quedó ningún cambio parcial.

  4. 04

    Crea PATCH /pedidos/:id/cancelar para cambiar el estado a CANCELADO en lugar de borrar historia.

Lo que viene

Desplegar y proteger

La API aún vive localmente y no distingue quién hace cada operación. Los siguientes retos son despliegue, autenticación y autorización: publicarla, reconocer identidades y limitar permisos.

Docker en una idea

Docker empaqueta aplicación y entorno en un contenedor reproducible. Resuelve diferencias entre máquinas y gana importancia al desplegar sistemas con infraestructura más compleja. No reemplaza el diseño de la aplicación ni siempre es obligatorio para publicar.

Cierre

¿Qué hizo que este catálogo pasara de “funciona” a “se puede integrar profesionalmente”?
Un contrato de entrada ejecutable, operaciones CRUD coherentes, errores con semántica HTTP, documentación navegable y pruebas que demuestran cada comportamiento.
