01 · Apertura

Una API que no sabe de quién son los datos

La privacidad no aparece por tener endpoints: nace cuando la API identifica a cada persona y aplica esa identidad en sus consultas.

Detente y decide

"Nuestra API de finanzas ya guarda transacciones y sobreviven al reinicio. Ahora imaginen que esto es una app real, publicada, con mil usuarios. Yo, desde Postman, hago GET /transacciones. ¿Qué me devuelve? ¿Las mías... o las de los mil usuarios?"

Primera intuición

"Las tuyas", "las de tu cuenta".

Criterio técnico

Las de los mil. Ahora mismo GET /transacciones devuelve absolutamente todas las transacciones de la base, sin distinguir de quién son. No existe el concepto de "usuario" todavía. Cualquiera que conozca la URL ve las finanzas de todo el mundo, y puede crear, editar y borrar lo de cualquiera. Es un desastre de privacidad y seguridad. Hoy resolvemos eso.

El problema real

Nuestra API tiene dos huecos graves:

  1. No sabe quién eres. No hay forma de identificar quién hace cada petición.
  2. No protege nada. Todos los endpoints están abiertos a cualquiera.

Una app de finanzas sin esto es inservible: los datos privados de una persona son visibles y editables por cualquier otra.

Conexión con el mapa del curso

  • Módulo 2 (lo anterior): construimos una API que guarda datos y valida su forma.
  • Hoy: le enseñamos a saber quién eres y a proteger lo que es tuyo.
  • Próxima clase: roles y permisos (que un administrador pueda hacer cosas que un usuario normal no).

Qué es este proyecto

finanzas-api es una API REST de finanzas personales con dos entidades:

  • Categoria — la clasificación del dinero (Comida, Salario, Arriendo).
  • Transaccion — cada movimiento de dinero, de tipo INGRESO o GASTO, que pertenece a una categoría.

Relación: una Categoría tiene muchas Transacciones (1 a N). Tiene CRUD completo en las dos, validaciones con DTOs, manejo de errores de Prisma y documentación Swagger.

import { PrismaPg } from '@prisma/adapter-pg';
import { PrismaClient } from '../generated/prisma/client';

@Injectable()
export class PrismaService
  extends PrismaClient
  implements OnModuleInit, OnModuleDestroy
{
  constructor() {
    const connectionString = process.env.DATABASE_URL;

    if (!connectionString) {
      throw new Error('DATABASE_URL no está definida. Revisa el archivo .env.');
    }

    const adapter = new PrismaPg({ connectionString });
    super({ adapter });
  }

  async onModuleInit(): Promise<void> {
    await this.$connect();
  }

  async onModuleDestroy(): Promise<void> {
    await this.$disconnect();
  }
}

Editarsrc/common/filters/prisma-exception.filter.ts
import {
  ArgumentsHost,
  Catch,
  ExceptionFilter,
  HttpStatus,
} from '@nestjs/common';
import { Response } from 'express';
import { Prisma } from '../../generated/prisma/client';

@Catch(Prisma.PrismaClientKnownRequestError)
export class PrismaExceptionFilter implements ExceptionFilter {
  catch(exception: Prisma.PrismaClientKnownRequestError, host: ArgumentsHost) {
    const response = host.switchToHttp().getResponse<Response>();

    switch (exception.code) {
      case 'P2025':
        return response.status(HttpStatus.NOT_FOUND).json({
          statusCode: HttpStatus.NOT_FOUND,
          message: 'El recurso solicitado no existe',
        });
      case 'P2002':
        return response.status(HttpStatus.CONFLICT).json({
          statusCode: HttpStatus.CONFLICT,
          message: 'Ya existe un registro con ese valor único',
        });
      case 'P2003':
        return response.status(HttpStatus.BAD_REQUEST).json({
          statusCode: HttpStatus.BAD_REQUEST,
          message: 'La relación referenciada no existe',
        });
      default:
        return response.status(HttpStatus.INTERNAL_SERVER_ERROR).json({
          statusCode: HttpStatus.INTERNAL_SERVER_ERROR,
          message: 'Error interno de base de datos',
        });
    }
  }
}

Detente y decide

"Después de que inicio sesión con mi correo y contraseña, hago diez peticiones más. ¿Debería mandar mi correo y contraseña en cada una de las diez?"

Primera intuición

"Sí, para que sepa que soy yo cada vez".

Criterio técnico

No. Mandar la contraseña en cada petición es inseguro (viaja mil veces) e incómodo. En vez de eso, al iniciar sesión el servidor te entrega un token: un carné temporal firmado. En las siguientes peticiones mandas el token, no la contraseña. El servidor confía en el token porque él mismo lo firmó.

Concepto esencial

Definición — JWT (JSON Web Token)

Técnica: un JWT es una cadena de texto firmada que transporta información de identidad de forma verificable. El servidor lo emite al iniciar sesión y el cliente lo presenta en cada petición.

En palabras sencillas: es un carné de entrada temporal. Dice quién eres, tiene fecha de vencimiento, y trae un sello que solo el servidor puede poner y reconocer.

Vida real: la manilla de un concierto. Pagas una vez en la entrada (login) y te ponen la manilla. Adentro no vuelves a pagar en cada puesto; solo muestras la manilla. Está diseñada para no poder falsificarse.

Las tres partes de un JWT

Un JWT tiene tres bloques separados por puntos: xxxxx.yyyyy.zzzzz

Este modelo conecta las piezas en el orden en que participan durante una petición real.

  • El payload no es secreto: cualquiera puede leerlo. Por eso nunca se mete una contraseña ahí.
  • La firma es lo que lo hace confiable: si alguien cambia una letra del payload, la firma deja de coincidir y el servidor lo rechaza.

¿Entonces cualquiera puede leer el contenido del token?

  • Sí, el payload es visible (está codificado, no cifrado). Por eso solo se guardan datos no sensibles: el id del usuario y su email, nunca la contraseña.
  • La seguridad no viene de esconder el contenido, sino de la firma: nadie puede fabricar un token válido sin el JWT_SECRET.

Explicación: El login busca al usuario por email, compara la contraseña con bcrypt, y si todo cuadra firma un JWT con el id y el email dentro. Agregamos el método login y los imports que necesita.

Antes del código

Reemplazarsrc/auth/auth.service.ts
import {
  ConflictException,
  Injectable,
  UnauthorizedException,
} from '@nestjs/common';
import { JwtService } from '@nestjs/jwt';
import * as bcrypt from 'bcrypt';
import { PrismaService } from '../prisma/prisma.service';
import { RegisterDto } from './dto/register.dto';
import { LoginDto } from './dto/login.dto';

@Injectable()
export class AuthService {
  constructor(
    private readonly prisma: PrismaService,
    private readonly jwtService: JwtService,
  ) {}

  async register(dto: RegisterDto) {
    const existente = await this.prisma.usuario.findUnique({
      where: { email: dto.email },
    });
    if (existente) {
      throw new ConflictException('El email ya está registrado');
    }

    const hash = await bcrypt.hash(dto.password, 10);

    const usuario = await this.prisma.usuario.create({
      data: { email: dto.email, password: hash, nombre: dto.nombre },
    });

    return { id: usuario.id, email: usuario.email, nombre: usuario.nombre };
  }

  async login(dto: LoginDto) {
    const usuario = await this.prisma.usuario.findUnique({
      where: { email: dto.email },
    });
    if (!usuario) {
      throw new UnauthorizedException('Credenciales inválidas');
    }

    const passwordOk = await bcrypt.compare(dto.password, usuario.password);
    if (!passwordOk) {
      throw new UnauthorizedException('Credenciales inválidas');
    }

    const payload = { sub: usuario.id, email: usuario.email };
    const access_token = await this.jwtService.signAsync(payload);

    return { access_token };
  }
}
Cómo se integra

Implementa el registro seguro y luego el login que compara el hash y firma el JWT.

Qué hace el login, paso a paso:

  1. Busca al usuario por email.
  2. Si no existe, lanza 401 con un mensaje genérico.
  3. Compara la contraseña escrita con el hash guardado usando bcrypt.compare.
  4. Si no coincide, lanza el mismo 401 genérico.
  5. Si todo cuadra, arma el payload (sub = id, más el email) y firma el JWT.
  6. Devuelve el token en access_token.
?

¿Por qué el mensaje de error es el mismo ("Credenciales inválidas") tanto si el email no existe como si la contraseña está mal?

  • Por seguridad. Si dijéramos "ese email no existe", un atacante podría probar correos hasta descubrir cuáles están registrados. Con un mensaje genérico, no revelamos si el fallo fue el email o la contraseña.
  • Es una decisión deliberada de un desarrollador senior: menos información al atacante.

"Ya entregamos el token al iniciar sesión. Cuando llega una petición con un token, ¿quién lo revisa, verifica la firma y saca de él quién es el usuario?"

Primera intuición

Criterio técnico

No queremos escribir esa revisión en cada endpoint (sería repetir código en todos lados). Usamos Passport, el motor de autenticación de NestJS, con una estrategia que sabe leer el token del encabezado, verificar la firma con el JWT_SECRET y entregar el usuario ya identificado. Se escribe una vez y se reutiliza.

Concepto esencial

Definición — Passport y su estrategia

Técnica: Passport es una librería de autenticación para Node. Una estrategia es un método concreto de autenticar; la nuestra, passport-jwt, autentica leyendo y verificando un JWT.

En palabras sencillas: Passport es el portero, y la estrategia es la instrucción que le damos: "revisa que traigan la manilla del concierto, y que sea auténtica".

Vida real: el portero de la discoteca no decide las reglas; sigue una instrucción (la estrategia): "deja entrar a quien traiga manilla válida". Cambias la instrucción y cambias cómo autentica, sin cambiar al portero.

Paso 7.1 — La estrategia JWT

Explicación: Define cómo se valida el token: lo saca del encabezado Authorization: Bearer ..., verifica la firma con el secreto, y con el payload arma el objeto de usuario que quedará disponible en la petición.

Antes del código

Editar este bloque en src/auth/jwt.strategy.ts. Extrae el Bearer token, verifica su firma y convierte el payload en un usuario autenticado.

Editarsrc/auth/jwt.strategy.ts
import { Injectable, UnauthorizedException } from '@nestjs/common';
import { PassportStrategy } from '@nestjs/passport';
import { ExtractJwt, Strategy } from 'passport-jwt';

type JwtPayload = { sub: number; email: string };

@Injectable()
export class JwtStrategy extends PassportStrategy(Strategy) {
  constructor() {
    const secret = process.env.JWT_SECRET;
    if (!secret) {
      throw new UnauthorizedException('JWT_SECRET no está definida');
    }
    super({
      jwtFromRequest: ExtractJwt.fromAuthHeaderAsBearerToken(),
      ignoreExpiration: false,
      secretOrKey: secret,
    });
  }

  validate(payload: JwtPayload) {
    return { id: payload.sub, email: payload.email };
  }
}
Cómo se integra

Extrae el Bearer token, verifica su firma y convierte el payload en un usuario autenticado.

Qué hace, paso a paso:

  1. Lee el token del encabezado Authorization: Bearer <token>.
  2. ignoreExpiration: false → un token vencido se rechaza.
  3. Verifica la firma con el JWT_SECRET.
  4. Si el token es válido, validate recibe el payload y devuelve el objeto de usuario.
  5. Ese objeto ({ id, email }) queda pegado a la petición para que los controladores lo usen.
?

¿Qué es "Bearer" en el encabezado?

  • Es el tipo de token que se usa en el estándar HTTP. Se escribe Authorization: Bearer <token>. La palabra Bearer significa "el portador": quien presente este token, se considera autenticado.
  • ⚠️ En Postman es un error clásico olvidar la palabra Bearer antes del token. Sin ella, la estrategia no encuentra el token y devuelve 401.

Paso 8.2 — Transacciones atadas al dueño

Explicación: Reescribimos el servicio de transacciones para que cada operación use el id del usuario autenticado. Al crear, se ata la transacción a su dueño; al listar, solo salen las suyas; al pedir una por id, se verifica que sea suya.

Antes del código

Reemplazarsrc/transacciones/transacciones.service.ts
import {
  ForbiddenException,
  Injectable,
  NotFoundException,
} from '@nestjs/common';
import { PrismaService } from '../prisma/prisma.service';
import { CrearTransaccionDto } from './dto/crear-transaccion.dto';
import { ActualizarTransaccionDto } from './dto/actualizar-transaccion.dto';

@Injectable()
export class TransaccionesService {
  constructor(private readonly prisma: PrismaService) {}

  crear(dto: CrearTransaccionDto, usuarioId: number) {
    return this.prisma.transaccion.create({
      data: {
        descripcion: dto.descripcion,
        monto: dto.monto,
        tipo: dto.tipo,
        categoriaId: dto.categoriaId,
        usuarioId,
      },
      include: { categoria: true },
    });
  }

  obtenerMias(usuarioId: number) {
    return this.prisma.transaccion.findMany({
      where: { usuarioId },
      include: { categoria: true },
      orderBy: { id: 'asc' },
    });
  }

  async obtenerUna(id: number, usuarioId: number) {
    const transaccion = await this.prisma.transaccion.findUnique({
      where: { id },
      include: { categoria: true },
    });

    if (!transaccion) {
      throw new NotFoundException('La transacción no existe');
    }

    if (transaccion.usuarioId !== usuarioId) {
      throw new ForbiddenException('Esta transacción no es tuya');
    }

    return transaccion;
  }

  async actualizar(
    id: number,
    dto: ActualizarTransaccionDto,
    usuarioId: number,
  ) {
    await this.obtenerUna(id, usuarioId);
    return this.prisma.transaccion.update({
      where: { id },
      data: dto,
      include: { categoria: true },
    });
  }

  async eliminar(id: number, usuarioId: number) {
    await this.obtenerUna(id, usuarioId);
    return this.prisma.transaccion.delete({ where: { id } });
  }
}
Cómo se integra

Concentra la persistencia de transacciones; en su versión protegida también aplica la propiedad del usuario.

Qué cambió respecto al estado inicial:

  1. Cada método ahora recibe usuarioId.
  2. crear ata la transacción a su dueño con usuarioId.
  3. obtenerMias filtra con where: { usuarioId } → solo las tuyas.
  4. obtenerUna verifica: si no existe → 404; si es de otro → 403.
  5. actualizar y eliminar reutilizan obtenerUna para comprobar la propiedad antes de tocar nada.
?

¿Por qué actualizar y eliminar llaman primero a obtenerUna?

  • Para no dejar que alguien edite o borre lo que no es suyo. Si no verificáramos, Luis podría borrar una transacción de Ana solo con saber su id.
  • obtenerUna ya trae la lógica de "existe y es tuya"; reutilizarla evita repetir esa comprobación. Es separación de responsabilidades: una sola función decide la propiedad.

  Body,
  Controller,
  Delete,
  Get,
  Param,
  ParseIntPipe,
  Patch,
  Post,
  UseGuards,
} from '@nestjs/common';
import { ApiBearerAuth, ApiTags } from '@nestjs/swagger';
import { JwtAuthGuard } from '../auth/jwt-auth.guard';
import { UsuarioActual } from '../auth/usuario-actual.decorator';
import { TransaccionesService } from './transacciones.service';
import { CrearTransaccionDto } from './dto/crear-transaccion.dto';
import { ActualizarTransaccionDto } from './dto/actualizar-transaccion.dto';

@ApiBearerAuth()
@UseGuards(JwtAuthGuard)
@Controller('transacciones')

  }

  @Patch(':id')
  actualizar(
    @Param('id', ParseIntPipe) id: number,

  @Delete(':id')

    @Param('id', ParseIntPipe) id: number,

  ) {

11 · Diagnóstico

Cómo leer los fallos y ubicar cada pieza

Los mensajes de compilación y HTTP señalan en qué capa está el problema; el mapa permite comprobar el alcance completo.

1. Property 'usuario' does not exist on type 'PrismaService'

  • Causa: se editó el schema pero no se corrió npx prisma migrate dev (o npx prisma generate). El cliente aún no conoce el modelo Usuario.
  • Solución: correr la migración y regenerar. El error #1 de hoy.

2. 401 Unauthorized con un token que parece correcto

  • Cómo se lee: el token existe pero no se aceptó.
  • Causa más común: falta la palabra Bearer antes del token, o se copió el token con espacios o incompleto.
  • Solución: en Postman usar Authorization → Bearer Token, o el header Authorization: Bearer <token> exacto.

3. 404 Not Found en /auth/register

  • Causa: AuthModule no está en el imports de app.module.ts.
  • Solución: agregarlo. "Si no lo importas, no existe."

4. secretOrPrivateKey must have a value

  • Cómo se lee: el JWT no se pudo firmar porque no encontró el secreto.
  • Causa: falta JWT_SECRET en el .env, o main.ts no tiene import 'dotenv/config' como primera línea.

Criterio técnico

Hoy todos los usuarios son iguales: cada uno ve lo suyo y nada más, sin excepción. No existe la idea de que unos puedan más que otros. Falta el concepto de rol (usuario vs. administrador) y de permisos por rol. Eso es exactamente lo que construiremos en la próxima clase: control de acceso basado en roles (RBAC), con guards que revisan no solo quién eres sino qué rol tienes.
