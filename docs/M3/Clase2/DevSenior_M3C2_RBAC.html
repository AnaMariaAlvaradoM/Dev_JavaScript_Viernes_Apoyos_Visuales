Paso 0.1 — La idea de fondo, en una frase

La Clase 1 le enseñó a finanzas-api dos cosas: saber quién eres (autenticación, con login + JWT) y que cada quien solo toque lo suyo (autorización básica, por propiedad/ownership). Hoy construimos un tercer nivel: que no todos los que se identifican pueden lo mismo (roles).

Para pensar

¿En qué paso de este diagrama se decide 'quién eres', y en qué paso se decide 'qué es tuyo'?

Ver respuesta

JwtAuthGuard + JwtStrategy deciden quién eres (autenticación).

Una primera intuición frecuente es: silencio, o "en el guard se decide todo".

03 · Ticket soporte

Un ticket que el ownership no resuelve

Soporte necesita ayudar sin suplantar al cliente ni conocer su contraseña.

Suplantar al cliente

Pedir una contraseña rompe la identidad, la auditoría y la confianza.

Permiso por función

Soporte conserva su propia identidad y recibe capacidades ampliadas por rol.

Para pensar

Llega un ticket de soporte: 'no veo reflejada mi transacción de ayer'. La persona de soporte de nuestra fintech necesita revisar los movimientos de ese usuario para ayudarlo. Con lo que construimos la clase pasada,

¿cómo hace soporte para ver esa transacción?

Ver respuesta

No puede, y pedir la contraseña sería gravísimo.

Con el ownership de hoy, cualquiera que no sea el dueño recibe 403 Forbidden, incluido el propio equipo de soporte. La única salida que se les ocurre (compartir contraseña) es una práctica de seguridad inaceptable: nadie, ni siquiera un desarrollador, debería conocer la contraseña real de otra persona. Falta un tercer concepto: que ciertos usuarios (administradores) tengan permisos ampliados, sin dejar de ser ellos mismos. Eso es RBAC.

Una primera intuición frecuente es: "Que soporte inicie sesión con la cuenta del usuario", o "que le pida la contraseña".

El problema real

Nuestra API distingue hoy solo dos cosas: con token o sin token, y dueño o no dueño. No existe una tercera categoría: alguien identificado, que no es el dueño, pero que por su cargo sí tiene permiso.

Conexión con el mapa del curso

  • Clase 1 (lo anterior): la API aprendió a identificarte (autenticación) y a proteger lo tuyo (autorización por propiedad).
  • Hoy: le enseñamos a la API a distinguir jerarquías: qué puede hacer un usuario normal frente a lo que puede hacer un administrador.
  • Próxima clase: seguiremos profundizando sobre la base de autenticación (ver "Para pensar" al cierre de esta guía).

04 · Modelo RBAC

Permisos agrupados por función

Autenticarse igual no significa poder hacer lo mismo.

👤Usuario

Ve y administra sus propios movimientos.

🛟Soporte

Atiende casos sin conocer contraseñas ajenas.

🛡️Administrador

Accede a operaciones ampliadas y auditables.

Para pensar

En Mercado Libre hay compradores, vendedores y empleados de soporte interno. Los tres inician sesión con el mismo sistema de login.

¿Debería el código de autenticación (JWT, bcrypt, Passport) ser distinto para cada uno de los tres?

Ver respuesta

No.

El login es el mismo para los tres: todos demuestran quién son de la misma forma. Lo que cambia no es cómo se autentican, sino qué se les permite hacer después. Un vendedor edita sus propios productos; soporte interno puede ver pedidos de cualquier comprador; un comprador solo ve los suyos. Esa diferencia se resuelve con roles, no con logins distintos.

Una primera intuición frecuente es: "Sí, cada tipo de usuario necesita su propio login".

Definición — RBAC (Role-Based Access Control)

Técnica: modelo de autorización donde los permisos no se asignan persona por persona, sino que se agrupan en roles, y cada usuario recibe uno o más roles. El sistema pregunta "¿qué rol tiene esta persona?" antes de decidir si puede ejecutar una acción.

En palabras sencillas: en vez de anotar "Juan puede borrar categorías, Ana no puede, Luis sí puede", defines el rol "administrador" con ese permiso, y a Juan y Luis simplemente les asignas ese rol.

Vida real: en un banco, el cargo de "cajero" trae consigo ciertos permisos, y el cargo de "gerente de sucursal" trae otros, sin importar quién ocupe ese cargo hoy. Si Juan deja de ser gerente, pierde esos permisos automáticamente: el permiso está atado al cargo, no a la persona.

Por qué RBAC y no permisos sueltos por usuario

Para pensar

¿Por qué no simplemente agregar una lista de permisos a cada usuario, en vez de un rol?

Ver respuesta

Porque con dos o tres usuarios no se nota,

pero con miles, mantener permisos individuales es insostenible: cada usuario nuevo requiere configurar sus permisos uno por uno.

Con roles, agregar un usuario nuevo es solo "asignarle un rol que ya existe". Es el mismo principio de no repetir lógica (DRY) aplicado a permisos.

05 · Arquitectura

Cuatro piezas, responsabilidades separadas

Diseña la cadena antes de escribir código y conserva el principio de responsabilidad única.

RBAC · una decisión antes del controlador
Campo rol

Fuente persistente.

JWT

Transporta el rol firmado.

@Roles

Declara la política.

RolesGuard

Hace cumplir la política.

Para pensar

En la Clase 1 dijimos: mostrar la cédula (autenticación) no es lo mismo que tener permiso para entrar a una oficina (autorización). Si ahora agregamos que la tarjeta de un gerente abre además la bóveda,

¿eso sigue siendo autenticación o es autorización?

Ver respuesta

Sigue siendo autorización.

La tarjeta (el JWT) identifica a la persona igual para todos; lo que cambia es qué puertas reconoce esa tarjeta como válidas para ella, y eso depende del cargo grabado en la tarjeta. RBAC es autorización, con un dato nuevo: el rol, que hoy vamos a grabar dentro del propio JWT.

Una primera intuición frecuente es: "Autenticación, porque es la misma tarjeta".

Las piezas nuevas que vamos a construir

Responsabilidades de la solución RBAC
PiezaResponsabilidad
Campo rol en UsuarioGuarda si el usuario es USUARIO o ADMIN
rol dentro del payload del JWTEl token ahora "sabe" el cargo de quien lo porta
@Roles(...) (decorador)Marca qué roles puede usar un endpoint
RolesGuardLee esa marca y compara contra el rol del usuario autenticado

¿Por qué un guard nuevo, y no meter la validación de rol dentro de JwtAuthGuard?

Para pensar

¿No sería más simple un solo guard que revise token y rol al tiempo?

Ver respuesta

Se podría, pero violaría el Principio de Responsabilidad Única (SOLID):

JwtAuthGuard tiene un solo trabajo, decidir "¿quién eres?".

Meterle también "¿qué puedes?" lo vuelve más difícil de mantener y de reutilizar. Con dos guards separados, JwtAuthGuard sirve para cualquier endpoint que solo necesite "estar logueado", y RolesGuard se agrega encima, solo donde además se necesita un rol específico. Se combinan, no se fusionan.

Cómo se van a encadenar los guards

ModeloFlujo de arquitectura
Petición → JwtAuthGuard (¿token válido?) → RolesGuard (¿el rol alcanza?)
        → Controller → Service → Prisma → PostgreSQL

Si JwtAuthGuard rechaza, ni siquiera se llega a RolesGuard. Los guards se ejecutan en orden, y todos deben aprobar para que la petición siga.

06 · Rol en datos

El rol nace seguro en PostgreSQL

USUARIO es el valor por defecto; el registro público nunca decide privilegios.

👤 Usuario
  • PK id
  • UQ email
  • rol · USUARIO por defecto
  • transacciones · relación 1:n
Para pensar

Vamos a agregar un campo rol al modelo Usuario. Cuando alguien se registre en POST /auth/register,

¿debería poder escribir en el body "rol": "ADMIN" y registrarse directamente como administrador?

Ver respuesta

Jamás.

Ya vimos con usuarioId en la Clase 1 que el backend nunca confía en datos sensibles que vengan del cliente. El rol es igual de sensible: si el DTO de registro aceptara rol, cualquier persona podría mandar "rol": "ADMIN" y auto-nombrarse administrador. Por eso todo usuario nuevo nace con el rol USUARIO por defecto, y el ascenso a ADMIN se hace por fuera del registro público (hoy, a mano, en la base de datos).

Una primera intuición frecuente es: "Sí, para que cada quien elija su tipo de cuenta al registrarse".

07 · JWT · firma

El rol entra al token

El login firma identidad y rol para evitar una consulta extra por petición.

Base de datosusuario.rol
→
Firmasub + email + rol
→
Peticiónrequest.user
Para pensar

El rol ya vive en la base de datos. Para que un guard pueda revisarlo en cada petición sin ir a preguntarle a la base de datos en cada una,

¿dónde más convendría tener ese dato disponible?

Ver respuesta

Dentro del propio JWT.

Ya guardamos ahí sub (el id) y email; agregamos rol al mismo payload. Así, cuando JwtStrategy valida el token, el rol viaja incluido, sin necesidad de una consulta extra a Postgres en cada petición protegida. Es el mismo principio del Bloque 6 de la Clase 1: el JWT transporta identidad de forma verificable, sin re-consultar la base a cada rato.

Una primera intuición frecuente es: "Consultando la base en cada petición".

Paso 5.1 — Incluir el rol al firmar el token

Explicación: En login(), el payload que se firma ahora incluye rol: usuario.rol. El método register() no cambia: como el schema ya pone USUARIO por defecto, Prisma lo asigna solo, sin que el código tenga que hacer nada extra.

Archivo: src/auth/auth.service.ts — versión final consolidada (reemplazar TODO):

Reemplazarsrc/auth/auth.service.ts
import {
  ConflictException,
  Injectable,
  UnauthorizedException,
} from '@nestjs/common';
import { JwtService } from '@nestjs/jwt';
import * as bcrypt from 'bcrypt';
import { PrismaService } from '../prisma/prisma.service';
import { RegisterDto } from './dto/register.dto';
import { LoginDto } from './dto/login.dto';

@Injectable()
export class AuthService {
  constructor(
    private readonly prisma: PrismaService,
    private readonly jwtService: JwtService,
  ) {}

  async register(dto: RegisterDto) {
    const existente = await this.prisma.usuario.findUnique({
      where: { email: dto.email },
    });
    if (existente) {
      throw new ConflictException('El email ya está registrado');
    }

    const hash = await bcrypt.hash(dto.password, 10);

    const usuario = await this.prisma.usuario.create({
      data: { email: dto.email, password: hash, nombre: dto.nombre },
    });

    return { id: usuario.id, email: usuario.email, nombre: usuario.nombre };
  }

  async login(dto: LoginDto) {
    const usuario = await this.prisma.usuario.findUnique({
      where: { email: dto.email },
    });
    if (!usuario) {
      throw new UnauthorizedException('Credenciales inválidas');
    }

    const passwordOk = await bcrypt.compare(dto.password, usuario.password);
    if (!passwordOk) {
      throw new UnauthorizedException('Credenciales inválidas');
    }

    const payload = {
      sub: usuario.id,
      email: usuario.email,
      rol: usuario.rol,
    };
    const access_token = await this.jwtService.signAsync(payload);

    return { access_token };
  }
}

Qué cambió respecto a la Clase 1: una sola línea nueva en el payload (rol: usuario.rol). Todo lo demás —hash, comparación, mensaje genérico de error— sigue igual.

Reemplazarsrc/auth/jwt.strategy.ts
import { Injectable, UnauthorizedException } from '@nestjs/common';
import { PassportStrategy } from '@nestjs/passport';
import { ExtractJwt, Strategy } from 'passport-jwt';
import { Rol } from '../generated/prisma/client';

type JwtPayload = { sub: number; email: string; rol: Rol };

@Injectable()
export class JwtStrategy extends PassportStrategy(Strategy) {
  constructor() {
    const secret = process.env.JWT_SECRET;
    if (!secret) {
      throw new UnauthorizedException('JWT_SECRET no está definida');
    }
    super({
      jwtFromRequest: ExtractJwt.fromAuthHeaderAsBearerToken(),
      ignoreExpiration: false,
      secretOrKey: secret,
    });
  }

  validate(payload: JwtPayload) {
    return { id: payload.sub, email: payload.email, rol: payload.rol };
  }
}

09 · @Roles

La ruta declara su política

Metadata tipada conecta la intención del endpoint con la decisión del guard.

Declaración

@Roles([Rol.ADMIN])

La ruta publica su requisito como metadata tipada.

Ejecución

RolesGuard

El guard lee la metadata y compara el rol autenticado.

Para pensar

Necesitamos que cada endpoint declare qué roles puede usarlo, sin repetir un if gigante dentro de cada método.

¿Cómo le 'pegamos una etiqueta' a un método de un controlador, para que algo externo la lea después?

Ver respuesta

En NestJS, eso se hace con metadata:

información adicional "pegada" a una clase o método, invisible en tiempo de ejecución normal, pero legible por un guard usando una herramienta llamada Reflector.

Vamos a crear un decorador @Roles([...]) que pega esa etiqueta, y un RolesGuard que la lee.

Una primera intuición frecuente es: "Con un comentario", "con el nombre del método".

Paso 6.1 — El decorador @Roles

Explicación: Reflector.createDecorator crea un decorador tipado: cuando lo usamos como @Roles([Rol.ADMIN]), guarda ese arreglo como metadata del método, lista para que un guard la consulte.

Generar por consola (Nest CLI):

Ejecutarfinanzas-api · terminal
nest g decorator auth/roles --flat

Archivo: src/auth/roles.decorator.ts (crear):

Crearsrc/auth/roles.decorator.ts
import { Reflector } from '@nestjs/core';
import { Rol } from '../generated/prisma/client';

export const Roles = Reflector.createDecorator<Rol[]>();
Para pensar

¿Por qué no usamos @SetMetadata('roles', [...]), que es lo que más se ve en tutoriales viejos?

Ver respuesta

SetMetadata funciona,

pero exige recordar la misma clave de texto ('roles') en el decorador y en el guard; si alguien la escribe distinto en un lado, falla en silencio.

Reflector.createDecorator es la forma recomendada hoy en la documentación oficial de NestJS: es genérica en TypeScript (Rol[]), así que si te equivocas de tipo, el compilador te avisa antes de correr nada.

10 · RolesGuard

El guard hace cumplir la política

Autenticar siempre ocurre antes de autorizar.

1

Leer la política

Reflector obtiene los roles del método actual.

2

Confirmar identidad

request.user ya existe gracias a JwtAuthGuard.

3

Comparar

El rol debe estar en la lista permitida.

4

Decidir

Continúa o responde 403 Forbidden.

Paso 6.2 — El RolesGuard

Explicación: Este guard lee la metadata que dejó @Roles(...) sobre el método. Si el método no tiene esa etiqueta, deja pasar (no todos los endpoints necesitan restricción de rol). Si la tiene, compara contra el rol del usuario ya autenticado.

Ejecutarfinanzas-api · terminal

import {
  CanActivate,
  ExecutionContext,
  ForbiddenException,
  Injectable,
} from '@nestjs/common';
import { Reflector } from '@nestjs/core';
import { Rol } from '../generated/prisma/client';
import { Roles } from './roles.decorator';

@Injectable()
export class RolesGuard implements CanActivate {
  constructor(private readonly reflector: Reflector) {}

  canActivate(context: ExecutionContext): boolean {
    const rolesRequeridos = this.reflector.get(Roles, context.getHandler());

    if (!rolesRequeridos) {
      return true;
    }

    const request = context.switchToHttp().getRequest();
    const usuario = request.user as { rol: Rol };

    if (!rolesRequeridos.includes(usuario.rol)) {
      throw new ForbiddenException('No tienes permiso para realizar esta acción');
    }

    return true;
  }
}

Qué hace, paso a paso:

  1. 1

    reflector.get(Roles, context.getHandler()) busca si el método actual tiene la etiqueta @Roles(...).

  2. 2

    Si no la tiene (undefined), deja pasar: ese endpoint no restringe por rol.

  3. 3

    Si la tiene, saca request.user (ya lo dejó ahí JwtStrategy) y compara su rol contra la lista permitida.

  4. 4

    Si no está en la lista, lanza 403 Forbidden con un mensaje claro.

Para pensar

¿Por qué RolesGuard puede leer request.user con confianza, sin volver a validar el token?

Ver respuesta

Porque RolesGuard siempre se coloca después de JwtAuthGuard en la cadena.

Para cuando RolesGuard se ejecuta, JwtAuthGuard ya validó el token y JwtStrategy ya dejó el usuario en la petición. RolesGuard confía en ese trabajo previo; no lo repite.

import {
  ForbiddenException,
  Injectable,
  NotFoundException,
} from '@nestjs/common';
import { PrismaService } from '../prisma/prisma.service';
import { CrearTransaccionDto } from './dto/crear-transaccion.dto';
import { ActualizarTransaccionDto } from './dto/actualizar-transaccion.dto';

@Injectable()
export class TransaccionesService {
  constructor(private readonly prisma: PrismaService) {}

  crear(dto: CrearTransaccionDto, usuarioId: number) {
    return this.prisma.transaccion.create({
      data: {
        descripcion: dto.descripcion,
        monto: dto.monto,
        tipo: dto.tipo,
        categoriaId: dto.categoriaId,
        usuarioId,
      },
      include: { categoria: true },
    });
  }

  obtenerMias(usuarioId: number) {
    return this.prisma.transaccion.findMany({
      where: { usuarioId },
      include: { categoria: true },
      orderBy: { id: 'asc' },
    });
  }

  obtenerTodasAdmin() {
    return this.prisma.transaccion.findMany({
      include: {
        categoria: true,
        usuario: { select: { id: true, nombre: true, email: true } },
      },
      orderBy: { id: 'asc' },
    });
  }

  async obtenerUna(id: number, usuarioId: number) {
    const transaccion = await this.prisma.transaccion.findUnique({
      where: { id },
      include: { categoria: true },
    });

    if (!transaccion) {
      throw new NotFoundException('La transacción no existe');
    }

    if (transaccion.usuarioId !== usuarioId) {
      throw new ForbiddenException('Esta transacción no es tuya');
    }

    return transaccion;
  }

  async actualizar(
    id: number,
    dto: ActualizarTransaccionDto,
    usuarioId: number,
  ) {
    await this.obtenerUna(id, usuarioId);
    return this.prisma.transaccion.update({
      where: { id },
      data: dto,
      include: { categoria: true },
    });
  }

  async eliminar(id: number, usuarioId: number) {
    await this.obtenerUna(id, usuarioId);
    return this.prisma.transaccion.delete({ where: { id } });
  }
}

14 · Helmet + CORS

Seguridad transversal

Middleware y guards protegen capas distintas de la petición.

Middleware

Helmet

Actúa igual sobre todas las respuestas, antes del contexto de la ruta.

Guard

JWT · Roles · Throttler

Decide con información de la ruta, la identidad o la política.

Para pensar

Helmet, que vamos a instalar ahora, agrega encabezados de seguridad a todas las respuestas de la API, sin importar qué controlador ni qué usuario esté detrás. No consulta request.user, no sabe qué ruta es.

¿Eso lo hace un guard o un middleware?

Ver respuesta

Un middleware.

Los guards (como JwtAuthGuard y RolesGuard) tienen acceso al ExecutionContext: saben qué controlador, qué método y qué usuario hay detrás de la petición. Un middleware, en cambio, corre antes, a nivel más bajo, sin ese contexto: solo ve la petición y la respuesta en crudo. Es la herramienta correcta para algo que aplica igual a todo, como encabezados de seguridad.

Una primera intuición frecuente es: "Un guard, porque también protege".

Definición — Helmet

Técnica: middleware de Express/Fastify que agrega un conjunto de encabezados HTTP de seguridad (contra clickjacking, sniffing de tipo de contenido, entre otros) a cada respuesta.

En palabras sencillas: son advertencias que el servidor le pone a cada respuesta para que el navegador de quien la reciba se comporte con más cuidado.

Vida real: es como el sello de seguridad en el empaque de un medicamento: no evita todos los problemas, pero reduce ataques conocidos y comunes con una sola línea de configuración.

15 · Límite global

Frenar la fuerza bruta

Un origen no puede intentar indefinidamente dentro de la misma ventana.

API global
10

Para pensar

Si alguien escribe un script que prueba mil contraseñas por segundo contra POST /auth/login,

¿qué se lo impide hoy?

Ver respuesta

Nada, a nivel de la API.

bcrypt hace que cada intento sea un poco más lento de calcular, pero no limita cuántos intentos por minuto puede hacer la misma persona o IP. Eso es un ataque de fuerza bruta, y se combate limitando la tasa de peticiones: rate limiting.

Una primera intuición frecuente es: "bcrypt lo hace lento", "nada".

Definición — Rate limiting

Técnica: mecanismo que restringe cuántas peticiones puede hacer un mismo origen (normalmente por IP) en una ventana de tiempo determinada. Al superar el límite, el servidor responde 429 Too Many Requests en vez de procesar la petición.

En palabras sencillas: es como una fila de banco con un guardia que solo deja pasar a cierta cantidad de personas cada minuto: no importa cuánta gente llegue, solo entra la cuota permitida.

Vida real: los bancos bloquean temporalmente una tarjeta después de tres intentos fallidos de PIN. La lógica es la misma: no eliminan el PIN, solo limitan cuántas veces se puede fallar en poco tiempo.

import { ThrottlerGuard, ThrottlerModule } from '@nestjs/throttler';
import { PrismaModule } from './prisma/prisma.module';

    PrismaModule,
    AuthModule,

import { ApiTags } from '@nestjs/swagger';
import { Throttle } from '@nestjs/throttler';
import { AuthService } from './auth.service';
import { RegisterDto } from './dto/register.dto';

@ApiTags('auth')
@Controller('auth')
export class AuthController {

  @Post('register')
  register(@Body() dto: RegisterDto) {
    return this.authService.register(dto);
  }

Checklist — buenas prácticas de autenticación que ya tiene finanzas-api

  • Contraseñas cifradas con bcrypt, nunca en texto plano.
  • Mensajes de error genéricos en login (no revelan si el email existe).
  • Tokens con expiración (1h), no eternos.
  • Secretos (JWT_SECRET) fuera del código, en .env.
  • Rol nunca autoasignable desde el registro público.
  • Límite de intentos en login (@Throttle), recién agregado.
  • Encabezados de seguridad con Helmet, recién agregado.

Copiloto para código sensible

Delega patrones; conserva las decisiones de seguridad y valida cada sugerencia.

“Agrégale roles”

Deja la restricción de seguridad a la imaginación del asistente.

Reglas explícitas

Para pensar

Si le pides a Cursor AI (o a cualquier asistente de código) 'agrégale roles a mi API de usuarios', y aceptas su primera sugerencia sin leerla,

¿qué es lo peor que podría pasar en un proyecto como este?

Ver respuesta

Lo peor no es que falle: es que compile y funcione, pero de forma insegura.

Un prompt vago como ese podría hacer que la IA agregue el campo rol directamente al RegisterDto —exactamente el error que evitamos en el Bloque 4— porque, sin más contexto, "agregar roles" suena a "que el usuario los elija". La IA no conoce las reglas de seguridad de tu proyecto a menos que se las des.

Una primera intuición frecuente es: "Que el código no compile", "que tenga un bug".

La IA como copiloto, no como piloto

Qué le puedes delegar a Cursor AI hoy: escribir el esqueleto repetitivo (DTOs, imports, un guard que sigue un patrón ya establecido). Qué nunca le delegas sin revisar: decisiones de seguridad — qué datos vienen del cliente y cuáles nunca, qué guard va en qué orden, qué se firma dentro de un JWT.

Cómo escribir un prompt seguro (comparación)

Prompt vago (riesgoso):

"Agrégale roles de admin y usuario a mi API."

Prompt con restricciones de seguridad (mejor):

"Agrega un enum Rol con USUARIO y ADMIN al modelo Usuario de Prisma, con USUARIO como valor por defecto. El campo rol nunca debe poder venir del body de una petición pública; solo se cambia manualmente en la base de datos. Incluye rol en el payload del JWT al hacer login."

Para pensar

¿Por qué el segundo prompt es mejor aunque sea más largo de escribir?

Ver respuesta

Porque explicita la restricción de seguridad,

en vez de dejar que la IA la infiera (y probablemente la infiera mal).

El tiempo que toma escribir un prompt así se recupera muchas veces en el tiempo que ahorras revisando —o corrigiendo en producción— una sugerencia insegura.

En palabras sencillas: es como dejarle al asistente un manual de estilo y de seguridad pegado en la pared de la oficina, que consulta antes de contestarte cualquier cosa.

# Seguridad de autenticación y autorización

- Nunca agregues un campo "rol" o "usuarioId" a un DTO que el cliente pueda
  enviar. El rol y el dueño de un recurso se asignan en el servidor, nunca
  vienen del body de la petición.
- Toda contraseña se cifra con bcrypt (factor de costo 10 o más). Nunca la
  guardes ni la registres en texto plano, ni en logs ni en consola.
- El JWT se firma solo con el algoritmo por defecto de @nestjs/jwt. Nunca
  sugieras deshabilitar la verificación de la firma.
- Todo endpoint que modifique datos debe pasar por JwtAuthGuard, y si aplica
  una restricción de rol, también por RolesGuard.
- Los mensajes de error de login y registro nunca deben revelar si un email
  existe o no en la base de datos.
- Nunca imprimas JWT_SECRET, un access_token completo, ni contraseñas en
  console.log ni en mensajes de error.

Checklist de revisión de código de autenticación generado por IA

Antes de aceptar una sugerencia de IA en código de login, JWT o roles, revisa:

  • ¿El algoritmo de firma del JWT sigue siendo el seguro por defecto (nunca "none")?
  • ¿Las verificaciones de rol están realmente presentes en cada endpoint que las necesita, o la IA asumió que "ya estaban"?
  • ¿Los mensajes de error siguen siendo genéricos, sin filtrar si un usuario existe?
  • ¿Algún dato sensible (rol, id de dueño) quedó expuesto en una respuesta o en un log?
  • ¿La sugerencia introduce una librería de autenticación que no conocías? Si es así, verifica su versión y su vigencia antes de instalarla.

Regla de oro del bloque: trata todo código de autenticación generado por IA como si lo hubiera escrito un desarrollador que nunca has conocido: se revisa igual, sin excepciones, aunque el código "se vea bien".

20 · Diagnóstico

Leer el error antes de tocar el código

Cinco señales frecuentes con causa y corrección concreta.

1. 403 Forbidden en un endpoint que "debería" dejar pasar a un administrador

  • Causa más común: el administrador está usando un token viejo, emitido antes de cambiarle el rol en la base.
  • Solución: volver a iniciar sesión para obtener un token con el rol actualizado.

2. @Roles([Rol.ADMIN]) puesto, pero el endpoint no protege nada

  • Causa: falta @UseGuards(RolesGuard) en ese mismo método (o en la clase). El decorador solo pone metadata; sin el guard, nadie la lee.
  • Solución: agregar @UseGuards(RolesGuard) junto al decorador.

3. Error de tipos con Rol al compilar

  • Causa: se importó Rol desde un archivo equivocado, o no se corrió npx prisma generate / migrate dev tras editar el schema.
  • Solución: confirmar el import (../generated/prisma/client) y volver a migrar.

4. 429 Too Many Requests inesperado durante las pruebas

  • Cómo se lee: no es un bug, es el ThrottlerGuard funcionando. Se hicieron más peticiones de las permitidas en la ventana de tiempo.
  • Solución: esperar unos segundos a que se reinicie la ventana, o reiniciar el servidor.

5. La migración del rol pide resetear la base

  • Causa: el campo rol se agregó sin @default(USUARIO).
  • Solución: siempre poner un valor por defecto cuando se agrega un campo obligatorio a una tabla con filas existentes.

Con lo que tenemos hoy,

no se puede revocar un JWT antes de que expire por sí mismo: es la naturaleza stateless del token (el servidor no lleva una lista de "tokens vivos").
