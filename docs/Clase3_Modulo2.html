Punto de partida

"La clase pasada le dimos memoria permanente al backend: los productos sobreviven al apagón. Ahora imaginen que soy un cliente malintencionado y mando este producto: nombre vacío, precio: -5000, stock: -999. Le doy Enviar. ¿Qué hace nuestra API con eso?"

Qué significa CRUD (por si quedó suelto)

Técnica: las cuatro operaciones básicas sobre cualquier dato persistente.

Letra Operación Verbo HTTP En la tienda
C Create (crear) POST Registrar un producto nuevo
R Read (leer) GET Ver el catálogo
U Update (actualizar) PATCH Corregir el precio
D Delete (eliminar) DELETE Quitar un producto descontinuado

Analogía: es el inventario de una bodega. Metes cajas (crear), revisas qué hay (leer), corriges una etiqueta mal puesta (actualizar), sacas lo que ya no sirve (eliminar). Todo sistema de datos del mundo hace estas cuatro cosas.

¿Por qué PATCH y no PUT para actualizar?

  • PUT reemplaza el registro entero: tienes que mandar todos los campos otra vez.
  • PATCH actualiza solo lo que mandas: si solo cambió el precio, mandas el precio.
  • Para editar un producto, PATCH es casi siempre lo que quieres. Es la opción cómoda y la más usada en la práctica.

"Si un type de TypeScript ya dice que precio es un número... ¿por qué entró el -5000? ¿No lo estaba validando ese type?"
Contrasta tu respuesta con la explicación técnica que sigue en esta sección.
  • Respuesta correcta: El type no existe cuando el programa corre. TypeScript es la receta (lo vimos en Módulo 1: .ts es la receta, .js el plato cocinado). Cuando el código se compila a JavaScript, todos los type desaparecen. En tiempo de ejecución no hay nadie revisando nada. El type ayuda a ti mientras escribes; no protege a la API cuando corre. Necesitamos algo que sí exista en ejecución: un DTO como clase, con reglas.

Definición de DTO

Técnica: un DTO (Data Transfer Object, objeto de transferencia de datos) es una clase que define la forma exacta que deben tener los datos que entran o salen de la API. A diferencia de un type, un DTO es una clase real: existe en tiempo de ejecución, y por eso podemos colgarle reglas de validación.

Analogía: el DTO es el formulario oficial de la entrada del edificio. No cualquier papel entra: tiene que ser ese formulario, con esas casillas llenas correctamente. El vigilante (la validación) revisa el formulario antes de dejar pasar a nadie. Un type era como decir "trae un papel"; el DTO dice "trae ESTE formulario, lleno así".

La diferencia con la Clase 2, en una frase: el type describía la forma para el editor; el DTO la impone para la API en ejecución.

Las dos librerías que hacen la magia

Explicación: NestJS no valida solo. Se apoya en dos librerías que trabajan juntas:

  • class-validator → aporta los decoradores de validación (@IsString(), @Min(), etc.). Es el que dice las reglas.
  • class-transformer → convierte el JSON que llega en una instancia real de la clase DTO, para que las reglas puedan aplicarse.

Dónde: en la terminal, en la raíz del proyecto.

CREAR Terminal / Postman 
import { IsString, IsNotEmpty, IsNumber, Min, IsInt, IsOptional } from 'class-validator';

export class CrearProductoDto {
  @IsString()
  @IsNotEmpty()
  nombre: string;

  @IsOptional()
  @IsString()
  descripcion?: string;

  @IsNumber()
  @Min(0)
  precio: number;

  @IsInt()
  @Min(0)
  stock: number;

  @IsInt()
  categoriaId: number;
}

Qué dice cada decorador

Se leen de arriba hacia abajo, como reglas apiladas sobre el campo:

  • @IsString() → tiene que ser texto.
  • @IsNotEmpty() → no puede venir vacío ("" se rechaza).
  • @IsNumber() → tiene que ser número.
  • @Min(0) → aquí muere el -5000. Mínimo cero.
  • @IsInt() → número entero (no tiene sentido stock: 3.5).
  • @IsOptional() → el campo puede no venir. Combina con el ? del schema: descripcion era opcional en la base, es opcional aquí.

La conexión con el schema (Clase 2): el DTO y el schema se dan la mano. En el schema, descripcion String? era opcional → aquí @IsOptional(). En el schema, precio Decimal no puede ser cualquier cosa → aquí @Min(0) le pone la regla de negocio.

¿El @Min(0) no debería estar en el schema de Prisma?

  • Prisma no valida rangos de negocio. Sabe de tipos (Int, Decimal), no de "positivo o negativo". Por eso el -5000 pasó en la Clase 2.
  • La regla de negocio ("el precio es positivo") vive en el DTO, en la puerta de entrada. Cada capa hace su trabajo: el schema define la estructura, el DTO define las reglas de quién puede entrar.
  • Analogía: el molde de la caja define su forma (schema); el vigilante define qué se permite meter en ella (DTO).

¿Por qué precio es @IsNumber pero stock es @IsInt?

  • El precio puede tener decimales (120000.50). El stock no: no existen "media unidad" de teclado. @IsInt es más estricto a propósito.
  • Es criterio de negocio traducido a código. Cada decorador es una decisión, no un adorno.

🚪 ValidationPipe

Antes de continuar

Antes de continuar

"Ya tenemos el formulario oficial (el DTO) con sus reglas. Si ahora mando el precio: -5000... ¿ya lo rechaza?"
Contrasta tu respuesta con la explicación técnica que sigue en esta sección.
  • Respuesta correcta: Todavía no. Escribir las reglas no basta: falta activar quien las haga cumplir. Es como tener el reglamento pegado en la pared pero sin vigilante que lo aplique. Ese vigilante es el ValidationPipe, y se activa una vez, globalmente, para toda la app.

Definición de Pipe

Técnica: un pipe en NestJS es una pieza que transforma o valida los datos que entran antes de que lleguen a tu controlador. Si los datos no cumplen, el pipe los rechaza ahí mismo — tu código de negocio ni se entera.

Analogía: es el filtro de agua antes del grifo. El agua pasa por el filtro antes de llegar a tu vaso. Si viene sucia, el filtro la detiene; tú nunca la ves. Ya conocen uno: en la Clase 2 usamos ParseIntPipe, que convertía el "1" de la URL en el número 1. Ese era un pipe de transformación. El ValidationPipe es de validación.

import { NestFactory } from '@nestjs/core';
import { ValidationPipe } from '@nestjs/common';
import { AppModule } from './app.module';

async function bootstrap() {
  const app = await NestFactory.create(AppModule);

  app.useGlobalPipes(
    new ValidationPipe({
      whitelist: true,
      forbidNonWhitelisted: true,
      transform: true,
    }),
  );

  await app.listen(3000);
}
bootstrap();

Las tres opciones, una por una

whitelist: true

  • Qué hace: borra automáticamente cualquier campo que no esté en el DTO. Si mandan { nombre, precio, hacker: true }, el hacker se elimina antes de tocar tu código.
  • Por qué importa: impide que inyecten campos que tú no esperabas.

forbidNonWhitelisted: true

  • Qué hace: en vez de borrar el campo intruso en silencio, rechaza toda la petición con un error 400 que dice "propiedad no permitida".
  • La diferencia con el anterior: whitelist limpia callado; forbidNonWhitelisted grita. Juntos: rechaza lo que no debería venir y te avisa.

transform: true

  • Qué hace: convierte el JSON plano en una instancia real de tu clase DTO. Sin esto, las reglas no se aplican correctamente. También convierte tipos automáticamente cuando puede.

¿whitelist y forbidNonWhitelisted no hacen lo mismo?

  • Casi. whitelist elimina los campos extra; forbidNonWhitelisted rechaza la petición entera por traerlos. Se usan juntos: el primero define qué se permite, el segundo castiga al que se sale.
  • Analogía: whitelist es el vigilante que te quita la botella en la puerta y te deja entrar; forbidNonWhitelisted es el que directamente no te deja entrar con ella. Activando los dos: no entra la botella y te devuelven en la puerta.

REEMPLAZAR Terminal / Postman 
import { Injectable } from '@nestjs/common';
import { PrismaService } from '../prisma/prisma.service';
import { CrearProductoDto } from './dto/crear-producto.dto';
import { ActualizarProductoDto } from './dto/actualizar-producto.dto';

@Injectable()
export class ProductosService {
  constructor(private readonly prisma: PrismaService) {}

  crear(datos: CrearProductoDto) {
    return this.prisma.producto.create({
      data: datos,
      include: { categoria: true },
    });
  }

  obtenerTodos() {
    return this.prisma.producto.findMany({
      include: { categoria: true },
      orderBy: { id: 'asc' },
    });
  }

  obtenerPorId(id: number) {
    return this.prisma.producto.findUniqueOrThrow({
      where: { id },
      include: { categoria: true },
    });
  }

  actualizar(id: number, datos: ActualizarProductoDto) {
    return this.prisma.producto.update({
      where: { id },
      data: datos,
      include: { categoria: true },
    });
  }

  eliminar(id: number) {
    return this.prisma.producto.delete({
      where: { id },
    });
  }
}

¿Por qué cambió findUnique por findUniqueOrThrow?

  • En la Clase 2 usábamos findUnique: si el producto no existía, devolvía null silenciosamente — y la API respondía 200 OK con un cuerpo vacío. Eso es mentira: dice "todo bien" cuando el producto no existe.
  • findUniqueOrThrow lanza un error (código P2025) si no encuentra nada. Ese error lo vamos a convertir en un 404 limpio en el Bloque 4. Es la base de "decir la verdad con códigos HTTP".
  • La misma idea aplica a update y delete: si el id no existe, Prisma lanza P2025 automáticamente. No tenemos que revisar a mano si existe antes de borrar.

import {
  Body,
  Controller,
  Delete,
  Get,
  Param,
  ParseIntPipe,
  Patch,
  Post,
} from '@nestjs/common';
import { ProductosService } from './productos.service';
import { CrearProductoDto } from './dto/crear-producto.dto';
import { ActualizarProductoDto } from './dto/actualizar-producto.dto';

@Controller('productos')
export class ProductosController {
  constructor(private readonly productosService: ProductosService) {}

  @Post()
  crear(@Body() datos: CrearProductoDto) {
    return this.productosService.crear(datos);
  }

  @Get()
  obtenerTodos() {
    return this.productosService.obtenerTodos();
  }

  @Get(':id')
  obtenerPorId(@Param('id', ParseIntPipe) id: number) {
    return this.productosService.obtenerPorId(id);
  }

  @Patch(':id')
  actualizar(
    @Param('id', ParseIntPipe) id: number,
    @Body() datos: ActualizarProductoDto,
  ) {
    return this.productosService.actualizar(id, datos);
  }

  @Delete(':id')
  eliminar(@Param('id', ParseIntPipe) id: number) {
    return this.productosService.eliminar(id);
  }
}

¿Dónde exactamente se dispara la validación?

  • En el @Body() datos: CrearProductoDto. Cuando el ValidationPipe está activo (Bloque 2) y ve que el body está tipado con una clase DTO, corre sus reglas antes de entrar al método.
  • Por eso el type de la Clase 2 no servía: no era una clase, el pipe no tenía dónde agarrarse. La clase DTO es el gancho.

¿Por qué el controller sigue tan delgado?

  • Porque el controller solo recibe y delega. Toda la lógica vive en el service. Es la separación de responsabilidades de la Clase 1: el mesero (controller) toma el pedido; el cocinero (service) lo prepara.
  • Esto no es casualidad ni estética: un controller delgado es fácil de leer, fácil de probar, fácil de cambiar. Es arquitectura limpia en la práctica.

Probar el CRUD completo en Postman

El ciclo entero, en orden:

  1. Crear → POST /productos con un body válido → guarda el producto, devuelve 201.
  2. Leer → GET /productos/1 → lo trae con su categoría.
  3. Actualizar → PATCH /productos/1 con solo { "precio": 99000 } → cambia solo el precio.
  4. Eliminar → DELETE /productos/1 → lo borra.
  5. Verificar → GET /productos/1 otra vez → ahora debe dar error (no existe).
05ARQUITECTURA

🌐 Errores HTTP

Antes de continuar

Antes de continuar

"Cuando borré el producto inexistente, salió un error 500 con un montón de texto de Prisma. Si yo fuera la app de un cliente consumiendo esta API... ¿qué entiendo de ese 500?"
Contrasta tu respuesta con la explicación técnica que sigue en esta sección.
  • Respuesta correcta: Nada útil, y peor: me confunde. Un 500 significa "error interno del servidor" — le echa la culpa al servidor. Pero el problema no fue del servidor: fue que pedí algo que no existe. Eso es un 404 Not Found. Los códigos HTTP son un idioma: 404 dice "no existe", 409 dice "conflicto, ya existe", 400 dice "tu petición está mal". Hablar ese idioma es lo que hace profesional a una API.

Los códigos HTTP que nos importan hoy

Técnica: el código de estado HTTP es un número que resume qué pasó con la petición. Categorías:

Rango Significa Ejemplo de hoy
2xx Todo bien 200 leído, 201 creado
4xx El cliente se equivocó 400 datos inválidos, 404 no existe, 409 conflicto
5xx El servidor se equivocó 500 bug real nuestro

La regla de oro: si el cliente mandó algo mal, es 4xx — no 5xx. Un 500 debe significar "de verdad se nos rompió algo". Devolver 500 cuando el cliente pidió un id inexistente es echarle la culpa al que no la tiene.

Analogía: en un restaurante, si pides un plato que no está en la carta, el mesero no dice "se incendió la cocina" (500). Dice "ese plato no lo tenemos" (404). Cada problema, su respuesta honesta.

Definición de Exception Filter

Técnica: un filtro de excepciones es una pieza de NestJS que intercepta los errores antes de que salgan al cliente, y decide qué respuesta HTTP enviar en su lugar. Es el traductor entre "el error técnico que ocurrió adentro" y "el mensaje HTTP honesto que sale afuera".

Analogía: es el vocero de prensa de la empresa. Adentro pasó un lío técnico (un P2025 de Prisma). El vocero no repite el lío crudo: lo traduce a un comunicado claro para el público ("el recurso no existe: 404"). Filtra el ruido interno y comunica con claridad.

Los códigos de error de Prisma que traducimos

Prisma no lanza errores HTTP (no sabe de HTTP, solo de base de datos). Lanza errores con códigos propios. Los tres de hoy:

Código Prisma Qué pasó Código HTTP correcto
P2025 El registro no existe (update/delete/find de algo ausente) 404 Not Found
P2002 Violación de restricción única (crear categoría repetida) 409 Conflict
P2003 Violación de clave foránea (categoría inexistente) 400 Bad Request

Los tres ya los "provocamos" sin querer en la Clase 2: el P2002 era el error de crear "Periféricos" dos veces; el P2003 era el categoriaId: 999. Hoy los volvemos respuestas amables.

import { ArgumentsHost, Catch, HttpStatus } from '@nestjs/common';
import { BaseExceptionFilter } from '@nestjs/core';
import { Prisma } from './generated/prisma/client';
import { Response } from 'express';

@Catch(Prisma.PrismaClientKnownRequestError)
export class PrismaExceptionFilter extends BaseExceptionFilter {
  catch(exception: Prisma.PrismaClientKnownRequestError, host: ArgumentsHost) {
    const contexto = host.switchToHttp();
    const respuesta = contexto.getResponse<Response>();

    switch (exception.code) {
      case 'P2025': {
        respuesta.status(HttpStatus.NOT_FOUND).json({
          statusCode: HttpStatus.NOT_FOUND,
          message: 'El recurso solicitado no existe.',
        });
        break;
      }
      case 'P2002': {
        respuesta.status(HttpStatus.CONFLICT).json({
          statusCode: HttpStatus.CONFLICT,
          message: 'Ya existe un registro con ese valor único.',
        });
        break;
      }
      case 'P2003': {
        respuesta.status(HttpStatus.BAD_REQUEST).json({
          statusCode: HttpStatus.BAD_REQUEST,
          message: 'La referencia indicada no existe (relación inválida).',
        });
        break;
      }
      default:
        super.catch(exception, host);
        break;
    }
  }
}

Leyendo el filtro por partes

  • @Catch(Prisma.PrismaClientKnownRequestError) → "solo me interesan los errores conocidos de Prisma". Los demás errores no los toca este filtro.
  • extends BaseExceptionFilter → hereda el comportamiento por defecto de Nest, para poder decir "en los casos que no manejo yo, hazte cargo tú" (el super.catch del default).
  • El switch → mira el .code del error y elige la respuesta HTTP.
  • El default → si es un error de Prisma que no listamos, deja que Nest responda su 500 normal. No ocultamos errores de verdad.

¿Por qué el default deja pasar el 500?

  • Porque un error que no anticipamos sí es un problema del servidor y merece un 500 honesto. El filtro traduce lo que sabemos interpretar; lo que no, lo deja como está. Ocultar errores desconocidos es peor que mostrarlos.

El problema nuevo: dos cosas que deben pasar juntas

Explicación: Cuando alguien compra, ocurren dos cosas:

  1. Se crea el pedido (con sus detalles).
  2. Se descuenta el stock de cada producto.

La pregunta peligrosa: ¿qué pasa si la primera funciona y la segunda falla? Quedaría un pedido registrado sin haber descontado stock. Vendiste algo que sigue figurando como disponible. Inventario corrupto.

Contrasta tu respuesta con la explicación técnica que sigue en esta sección.

Definición de transacción

Técnica: una transacción agrupa varias operaciones de base de datos en una sola unidad indivisible: o se completan todas, o no se aplica ninguna. Si algo falla a mitad de camino, la base deshace todo lo hecho hasta ahí (rollback), como si nada hubiera pasado.

Analogía: una transferencia bancaria. Restar de tu cuenta y sumar a la otra son dos pasos, pero tienen que pasar juntos. Imagina que resta de tu cuenta y falla antes de sumar a la otra: tu dinero desaparece. El banco lo hace como transacción: o los dos pasos, o ninguno. Nunca a medias.

En nuestro caso: crear el pedido y descontar el stock son una sola transacción. Si el descuento falla (stock insuficiente), el pedido no se crea. Todo o nada.

import { Type } from 'class-transformer';
import {
  IsInt,
  IsArray,
  ValidateNested,
  ArrayNotEmpty,
  Min,
} from 'class-validator';

export class ItemPedidoDto {
  @IsInt()
  productoId: number;

  @IsInt()
  @Min(1)
  cantidad: number;
}

export class CrearPedidoDto {
  @IsInt()
  usuarioId: number;

  @IsArray()
  @ArrayNotEmpty()
  @ValidateNested({ each: true })
  @Type(() => ItemPedidoDto)
  items: ItemPedidoDto[];
}

¿Qué hacen @ValidateNested y @Type?

  • Por defecto, la validación no entra en los objetos de una lista: vería items como "un arreglo" y no revisaría cada item adentro.
  • @ValidateNested({ each: true }) le dice: "valida cada objeto de la lista con sus propias reglas".
  • @Type(() => ItemPedidoDto) le dice con qué clase validar cada uno. Sin esto, no sabe que cada item es un ItemPedidoDto.
  • Juntos: garantizan que ningún item traiga cantidad: 0 o cantidad: -3. El @Min(1) de adentro sí se aplica.

¿Por qué @ArrayNotEmpty?

  • Un pedido sin productos no tiene sentido: sería una compra vacía. @ArrayNotEmpty rechaza items: []. Es una regla de negocio: no existen pedidos fantasma.

import { Injectable, BadRequestException } from '@nestjs/common';
import { PrismaService } from '../prisma/prisma.service';
import { CrearPedidoDto } from './dto/crear-pedido.dto';

@Injectable()
export class PedidosService {
  constructor(private readonly prisma: PrismaService) {}

  async crear(datos: CrearPedidoDto) {
    const idsProductos = datos.items.map((item) => item.productoId);

    const productos = await this.prisma.producto.findMany({
      where: { id: { in: idsProductos } },
    });

    const detalles = datos.items.map((item) => {
      const producto = productos.find((p) => p.id === item.productoId);

      if (!producto) {
        throw new BadRequestException(
          `No existe el producto con id ${item.productoId}.`,
        );
      }

      if (producto.stock < item.cantidad) {
        throw new BadRequestException(
          `Stock insuficiente de "${producto.nombre}": ` +
            `quedan ${producto.stock}, se pidieron ${item.cantidad}.`,
        );
      }

      return {
        productoId: producto.id,
        cantidad: item.cantidad,
        precioUnitario: producto.precio,
      };
    });

    const total = detalles.reduce(
      (suma, d) => suma + Number(d.precioUnitario) * d.cantidad,
      0,
    );

    return this.prisma.$transaction(async (tx) => {
      const pedido = await tx.pedido.create({
        data: {
          usuarioId: datos.usuarioId,
          total,
          detalles: { create: detalles },
        },
        include: {
          usuario: true,
          detalles: { include: { producto: true } },
        },
      });

      for (const detalle of detalles) {
        await tx.producto.update({
          where: { id: detalle.productoId },
          data: { stock: { decrement: detalle.cantidad } },
        });
      }

      return pedido;
    });
  }

  obtenerTodos() {
    return this.prisma.pedido.findMany({
      include: {
        usuario: true,
        detalles: { include: { producto: true } },
      },
      orderBy: { id: 'asc' },
    });
  }

  obtenerPorId(id: number) {
    return this.prisma.pedido.findUniqueOrThrow({
      where: { id },
      include: {
        usuario: true,
        detalles: { include: { producto: true } },
      },
    });
  }

  cancelar(id: number) {
    return this.prisma.pedido.update({
      where: { id },
      data: { estado: 'CANCELADO' },
    });
  }
}

Leyendo la transacción

  • this.prisma.$transaction(async (tx) => { ... }) → abre la transacción. Todo lo que pase con tx adentro es una sola unidad.
  • Ojo: dentro de la transacción usamos tx.pedido, tx.producto — no this.prisma. Ese tx es la mano de la transacción.
  • El for recorre los detalles y descuenta el stock de cada producto con decrement.
  • Si cualquier paso falla, Prisma deshace todo: ni pedido, ni descuento. Todo o nada.

¿Qué es decrement?

  • Es la forma de Prisma de decir "réstale esta cantidad al valor actual". stock: { decrement: 2 } = "quítale 2 al stock que haya".
  • Por qué no leer el stock, restar en JavaScript, y guardar: porque entre leer y guardar, otra compra podría cambiarlo. decrement lo hace en un solo paso, en la base, sin ese hueco. Es más seguro.

¿Por qué la verificación de stock está ANTES de la transacción?

  • Para fallar rápido: si no hay stock, ni empezamos. Pero fíjense que el decrement real ocurre dentro de la transacción, protegido. La verificación previa es cortesía; la transacción es la garantía.

El controller de Pedido: nota qué NO tiene

Explicación: Fíjense en lo ausente: no hay @Patch de edición general ni @Delete. En su lugar, un @Patch(':id/cancelar'). El diseño del controller refleja la regla de negocio.

import {
  Body,
  Controller,
  Get,
  Param,
  ParseIntPipe,
  Patch,
  Post,
} from '@nestjs/common';
import { PedidosService } from './pedidos.service';
import { CrearPedidoDto } from './dto/crear-pedido.dto';

@Controller('pedidos')
export class PedidosController {
  constructor(private readonly pedidosService: PedidosService) {}

  @Post()
  crear(@Body() datos: CrearPedidoDto) {
    return this.pedidosService.crear(datos);
  }

  @Get()
  obtenerTodos() {
    return this.pedidosService.obtenerTodos();
  }

  @Get(':id')
  obtenerPorId(@Param('id', ParseIntPipe) id: number) {
    return this.pedidosService.obtenerPorId(id);
  }

  @Patch(':id/cancelar')
  cancelar(@Param('id', ParseIntPipe) id: number) {
    return this.pedidosService.cancelar(id);
  }
}

¿Por qué /pedidos/1/cancelar y no DELETE /pedidos/1?

  • Porque la URL cuenta lo que de verdad pasa. DELETE diría "esto desaparece"; cancelar dice "esto cambia de estado y se conserva". La ruta honesta comunica la intención real.
  • Es diseño de API con criterio: el endpoint refleja el negocio, no una plantilla genérica.

09DIAGNÓSTICO

🧰 Errores comunes

1. Las validaciones no corren (el -5000 sigue entrando)

  • Causa: falta activar el ValidationPipe global en main.ts, o el @Body() no está tipado con la clase DTO.
  • Solución: revisar el Bloque 2. Es el olvido #1 del día.

2. Cannot read properties of undefined / decorador no es función

  • Cómo se lee: menciona un decorador de validación.
  • Causa: falta npm i class-validator class-transformer.

3. El filtro de errores no compila / no encuentra Prisma

  • Causa: importaron Prisma desde @prisma/client en vez de ./generated/prisma/client.
  • Solución: el import correcto para ESTE proyecto es el output custom de la Clase 2. El error que van a copiar de internet.

4. PartialType no existe

  • Causa: falta npm i @nestjs/mapped-types.

5. La transacción no descuenta stock

  • Causa: usaron this.prisma.producto.update en vez de tx.producto.update dentro de la transacción.
  • Cómo se lee: el descuento ocurre "por fuera" y rompe la garantía todo-o-nada.

6. 400 Bad Request inesperado con "property should not exist"

  • Cómo se lee: es forbidNonWhitelisted funcionando. Mandaron un campo que el DTO no declara.
  • Solución: es correcto — están mandando basura. Revisar el body.
